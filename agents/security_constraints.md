# Ограничения безопасности (Security & Protection Constraints)
## Для: Backend & Frontend Agents | Проект: Smart Enterprise Hub

Данный документ устанавливает обязательные требования к защите данных, изоляции тенантов, безопасной обработке файлов и предотвращению уязвимостей по стандарту OWASP Top 10.

---

## 1. 🛡️ Главный закон мультиарендности: Полная изоляция клиентов

1. **Никакого доверия к `company_id` от клиента**:
   - `company_id` **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** принимать из тела запроса (JSON body) или URL query-параметров от пользователя для определения прав.
   - Идентификатор компании извлекается **ИСКЛЮЧИТЕЛЬНО** на бэкенде из валидированного криптографического JWT-токена (`token.company_id`).
2. **Обязательная фильтрация всех SQL-запросов**:
   - Любая операция выборки (`SELECT`), обновления (`UPDATE`) или удаления (`DELETE`) обязана содержать условие `WHERE company_id = current_user.company_id`.
   - Нарушение этого правила расценивается как критическая уязвимость (IDOR / утечка корпоративных данных конкурентам).

---

## 2. 📁 Безопасность загрузки и обработки файлов (File Ingestion Security)

1. **Защита файловой системы от Path Traversal**:
   - Исходное имя файла от пользователя (`original_name`, например `../../etc/passwd` или `отчет.xlsx`) **никогда не используется** в качестве пути на сервере.
   - Файлы на диске сохраняются только под SHA-256 хешем с расширением: `storage/tenants/{company_id}/{YYYY}/{MM}/{sha256_hash}.xlsx`.
2. **Лимиты и защита от DoS (Zip Bomb / OOM)**:
   - Жесткий лимит на размер входящего потока: **не более 25 МБ**. Попытки загрузить больший файл обрываются на уровне Nginx/FastAPI потока (`HTTP 413 Payload Too Large`).
   - При парсинге `.xlsx` (который является ZIP-архивом) библиотеки `openpyxl` и `calamine` должны распаковывать файлы с ограничением размера памяти, исключая атаку «архивная бомба» (decompression bomb).
3. **Безопасная отдача файлов**:
   - Файлы никогда не лежат в открытом статическом каталоге Nginx.
   - Скачивание только через эндпоинт `GET /api/v1/files/{id}/download`, проверяющий принадлежность файла компании текущего пользователя.

---

## 3. 🔑 Аутентификация, Пароли и JWT

1. **Хеширование паролей**:
   - Запрещено использовать слабые алгоритмы (MD5, SHA1, чистый SHA256).
   - Разрешено: только надежное хеширование с солью через **`bcrypt`** (cost factor >= 12) или **`argon2id`**.
2. **JWT-токены**:
   - `access_token` живет не более **60 минут**.
   - `refresh_token` живет не более **14 дней** и хранится в защищенном виде.
   - Секретный ключ `JWT_SECRET` должен загружаться строго из переменной окружения `.env`.

---

## 4. 🚫 Защита от утечки секретов и отладочной информации

1. **Никаких секретов в коде**:
   - В коде, коммитах и репозитории **запрещены хардкоды** API-ключей (Gemini API Key, Telegram Bot Token, паролей от БД). Все передается через `pydantic-settings` и переменные окружения.
2. **Маскирование внутренних ошибок сервера**:
   - Клиент никогда не должен получать в ответе внутренние трейсбеки Python (`Traceback (most recent call last)`), имена внутренних таблиц или SQL-запросы.
   - Любое непредвиденное исключение логируется на сервере, а клиенту возвращается стандартизированный JSON:
     ```json
     {
       "success": false,
       "error": { "code": "INTERNAL_SERVER_ERROR", "message": "Произошла внутренняя ошибка сервера" }
     }
     ```
3. **CORS (Cross-Origin Resource Sharing)**:
   - Запрещен `allow_origins=["*"]` в связке с передачей учетных данных. Разрешены только доверенные домены клиента.
