# Проект интерфейсов первой волны FE-01 и FE-02

Маршруты экранов ниже предлагаем для реализации. Вызовы и состояния сверены с [контрактом BE-00](backend_contract.md). [Бэклог](../../tasks/frontend.md) · [Архитектура доступа](architecture.md) · [Операции поддержки](operations.md).

## Текущее состояние и переход

App.tsx определяет раздел по hash, загружает данные и показывает общую навигацию. AuthContext сохраняет токены в localStorage. api/client.ts читает токен оттуда и кеширует загрузки разделов. RoleContext сохраняет выбранную роль. Клиентская часть уже использует React и TypeScript, react-router-dom есть в зависимостях. FastAPI раздаёт статику через StaticFiles, поэтому проверка обновления страницы на вложенном пути входит в интеграцию. Для новых путей нужен ограниченный SPA fallback, который сохраняет обычные 404 API и ресурсов.

Существующие предметные экраны, включая сводку по двум листам, подключаем к новой оболочке без переписывания расчётов. Ссылки вида #procurement?due в переходный период преобразуем в маршрут разрешённого раздела с сохранением фильтра. URL с чужим кодом при активной сессии показывает нейтральный экран и предлагает выйти для входа по другой ссылке. Данные сессии нельзя показывать под чужим адресом.

## FE-01. Клиентский кабинет

| Маршрут | Экран и действия | Состояния и ограничения |
| --- | --- | --- |
| /login и /c/:code/login | Email, пароль и код. В ссылке код заполнен. После проверки открывается доступный обзор или разрешённый исходный маршрут | Неверные реквизиты и неизвестная компания дают одинаковое сообщение. После ограничения попыток показать время ожидания, если API его даёт |
| /c/:code/invite и /c/:code/reset | Ввод нового пароля, подтверждение, переход ко входу. При принятии приглашения также запросить имя. Отдельная форма запроса восстановления | Одинаковое подтверждение запроса восстановления независимо от существования адреса. Непригодная ссылка предлагает новый запрос или обращение к поддержке |
| /c/:code и /c/:code/m/:module | Обзор, навигация по каталогу и предметные экраны | Рисовать меню после bootstrap. Модуль с отключённым доступом даёт нейтральное сообщение и ссылку на обзор. Состояния нет данных и устаревших данных различаются |
| /c/:code/team | Список команды, редактирование имени, смена уровня доступа, блокировка и заявка на нового сотрудника | Видно директору. Подтверждение блокировки объясняет отзыв сессий. Последнего директора защищает API. Заявка показывает статус обработки |
| /c/:code/audit | Фильтры по периоду, автору, действию, список и детали события | Видно директору. В деталях только разрешённые поля, предыдущие и новые значения в том объёме, который вернул сервер |
| /c/:code/sources | Состояние интеграций, последний успех, следующая попытка, состояние данных | Сотрудник видит источники разрешённых модулей. При сбое показывать последнее подтверждённое состояние и время обновления |

Для MFA директора использовать промежуточный экран проверки фактора в маршруте входа. Пока сервер не подтвердил MFA, клиент не запускает загрузки защищённых экранов. После приёма приглашения и восстановления очистить токен из адреса и локального состояния. Для ссылки предпочесть секрет во fragment по согласованию с бэкендом. Отключить внешние ресурсы и передачу Referer на экранах приёма секретов. Переход после входа только на разрешённый внутренний путь той же компании.

## FE-02. Панель платформы

Панель имеет отдельную точку входа и сессию. Ниже пути относительно origin панели. Поддержка и владелец используют одну оболочку, допустимые действия приходят из серверных разрешений.

| Маршрут | Что видит оператор | Основные действия |
| --- | --- | --- |
| /login | Ввод реквизитов, затем MFA | Повторить проверку в пределах лимита или начать вход заново, если challenge истёк |
| /companies | Поиск, фильтры по состоянию, компания, модули, свежесть, открытые инциденты | Открыть карточку. Создать черновик, если действие разрешено |
| /companies/:id | Обзор, дата последнего успеха, общий статус платформы отдельно от состояния клиента | Перейти к источнику, настройке, приглашениям или инцидентам |
| /companies/:id/integrations/:integrationId | Статус, версия адаптера, список попыток и влияние на данные | Проверить подключение, запросить предпросмотр, безопасно повторить запуск с причиной |
| /companies/:id/incidents/:incidentId | Понятная причина, влияние, следующий шаг, ответственный, история переходов | Назначить ответственного, перевести состояние, скопировать обезличенную сводку |
| /companies/:id/invitations | Ожидающие и принятые приглашения, срок действия и связанные заявки | Выдать, перевыпустить или отозвать в пределах разрешений |
| /companies/:id/config | Ревизия, каталог модулей и параметры источников | Сохранить черновик, показать отличия, запросить предпросмотр, опубликовать либо откатить |
| /audit | История действий поддержки | Фильтрация в пределах прав владельца |

Безопасный повтор получает отдельное подтверждение и показывает запуск, который вернул API. Кнопка блокируется на время отправки. При потере ответа повторить тот же запрос с тем же Idempotency-Key. Дедупликация обеспечивается API. Отправлять expected_integration_version, а при изменённом профиле также approved_preview_id. Просмотр перед публикацией конфигурации показывает ревизию, агрегаты и предупреждения из административной проекции. В панели отсутствуют сырые строки импорта, секреты и клиентские документы. Смена ревизии во время редактирования предлагает перечитать текущую версию и сверить черновик.

## Сессия, данные и ошибки

- Клиентский namespace — /api/v1/auth и /api/v1/company. Панель — /api/v1/platform/auth и /api/v1/platform/companies. Использовать согласованный ResponseEnvelope. Клиентский bootstrap загружает GET /auth/me и GET /company/modules. Платформенный bootstrap использует GET /platform/auth/me.
- Cookies отправляются запросом браузера по согласованной политике origin. Получить csrf_token через GET /auth/csrf или GET /platform/auth/csrf до входа и повторно после входа или ротации. Передавать его в X-CSRF-Token для мутаций. Старые локальные auth-данные удаляются при переходе. Роль и права берутся из авторизованного ответа, тема может оставаться в localStorage.
- В состоянии bootstrap не отображать содержимое кабинета. При смене сессии отменять незавершённые запросы и очистить кеши. Защита от опоздавшего ответа через идентификатор поколения сессии. Ключи кеша и дедупликации включают идентичность контура и компании. При смене разрешений перечитать bootstrap и закрыть утративший доступ экран.
- 401 в защищённом контуре обрабатывать единым механизмом с одним refresh, для SESSION_REQUIRED. После провала очистить защищённое состояние и вернуть на вход. 403 показывает ограничение доступа, при COMPANY_PAUSED скрывает защищённые данные, 404 — нейтральное отсутствие, 429 — ограничение частоты. Повтор мутаций только по согласованному ключу и правилам API.
- Пустой список отличается от сбоя сети, загрузки и недоступности сервиса. При обновлении с ошибкой можно оставить последнее подтверждённое состояние той же активной сессии и явно указать время. При отзыве доступа скрыть прежние данные.
- Списки фильтруются с пагинацией и сортировкой API. Опоздавший запрос не заменяет результат нового фильтра. Ошибки формы связаны с полями, статус обновления доступен скринридеру, фокус возвращается после диалогов. Цвет статуса дублируется текстом.

## Разделение работ и порядок интеграции

| Исполнитель | Файлы и ответственность |
| --- | --- |
| FE-01 | App.tsx, context/AuthContext.tsx, context/RoleContext.tsx, features/auth, новые features/company, адаптация клиентских экранов и текущего api/client.ts |
| FE-02 | Новые features/platform, отдельный api/platformClient.ts и самостоятельная оболочка платформенной части |
| Ответственный за интеграцию | Согласованные типы API, точки входа и правила локального SPA fallback. Единолично объединяет общие изменения main.tsx, сборки и общих API-типов |

До фиксации BE-00 можно проектировать экраны и состояния на синтетических данных в тестовом контуре. После BE-02 подключить вход и сессии, после BE-03 меню и конфигурации, после BE-04 состояния источников, после BE-05/06 аудит и панель. В рабочем кабинете предметные данные приходят из API.

## Проверки для QA

1. Перейти по ссылке с кодом, войти, обновить вложенный путь, проверить прямую ссылку на выключенный раздел и подмену кода.
2. Выйти в одном окне во время загрузки и войти в другую компанию. Поздний ответ первой компании и переход назад не возвращают её данные.
3. Директор отключает сотрудника и находит своё действие в журнале. Открытый кабинет сотрудника теряет доступ на следующей проверке сессии.
4. Просроченная, отозванная и повторно открытая ссылки приводят к понятному экрану восстановления доступа. Платформенный вход без MFA не открывает список компаний.
5. Оператор находит неуспешный импорт, копирует обезличенные детали, дважды отправляет повтор, видит один запуск и закрывает инцидент после проверки.
6. У действующего демо-профиля открывается тендерная сводка. Пустая сумма сохраняется как неизвестная, ручная стадия остаётся видимой.

## Привязка к BE-00

- Для MFA использовать step, challenge_id и expires_at. При mfa_enrollment_required вызвать setup, затем verify. Приглашение, сброс пароля и смена адреса передают токен в POST.
- Чтение платформенных событий, запусков и инцидентов разделено. Историю собирает контейнер экрана из /events и /runs, поскольку IncidentSummary содержит только текущую сводку.
- Переходы инцидента передают version, to, reason и при необходимости assignee_id. Публикация и откат конфигурации передают expected_active_revision. При 409 обновить состояние и показать конфликт, сохранив локальные поля формы.
- Копируемый контекст инцидента ограничен кодом, временем и идентификаторами запуска и запроса, если они получены из соответствующих проекций. Сверка строк предпросмотра проходит в клиентском контуре.

## Точки входа реализации

Кабинет компании подключён через /c/:code и дочерние пути. Для входа с корневого адреса в централизованном режиме сборка получает VITE_PLATFORM_CLIENT=true, API использует PLATFORM_AUTH_ENABLED=true. Панель использует /platform на origin платформы. В режиме платформенных cookie Origin браузера и origin API должны совпасть для каждого из кабинетов. Legacy-точка входа остаётся доступна в режиме демо.
