# QA-02. Протокол интеграционной приёмки

Проверки выполняются на синтетических компаниях в одноразовой PostgreSQL 16, из копии приложения без рабочего .env. Файлы и почта находятся во временных каталогах. HTTP-тесты используют ASGI и настоящие маршруты, модели и политики PostgreSQL. Результаты браузерной приёмки и коммерческой готовности учитываются отдельно.

## Как повторить

Из корня проекта в PowerShell:

```powershell
.\.venv\Scripts\python.exe backend/tests/platform_pilot/run.py --postgres-bin 'C:/Program Files/PostgreSQL/16/bin'
.\.venv\Scripts\python.exe backend/tests/platform_pilot/run.py --tenant-rls-only --postgres-bin 'C:/Program Files/PostgreSQL/16/bin'
npm.cmd --prefix frontend run build
.\.venv\Scripts\python.exe backend/tests/platform_pilot/run.py --postgres-bin 'C:/Program Files/PostgreSQL/16/bin' --chrome-bin 'C:/Program Files/Google/Chrome/Application/chrome.exe'
```

Для локализации ошибок есть отдельные режимы --operations-only и --integrations-only. В обычном режиме runner выполняет сценарии последовательно в одном кластере. Очередь и обработчик стартуют по явным вызовам тестов, без внешнего Google Drive. Для браузерного сценария используются установленный Chrome в headless-режиме, временный профиль, локальный HTTPS-сервер и два тестовых origin. Системные настройки сертификатов и профиль рабочего браузера в тесте не меняются.

## Сценарии и границы покрытия

| Сценарий | Проверка | Граница |
| --- | --- | --- |
| Две компании | Тендерный реестр и реестр оборудования проходят durable preview и импорт на двух компаниях. В legacy-сценарии совпадают имя файла и номер записи, проверяется раздельная выдача. Через API проверены черновик, публикация конфигурации, приглашение, активация и первый вход директора. Опубликованная конфигурация ограничивает доступ к модулю и откатывается | Полный проход через интерфейсы остаётся браузерной проверкой |
| Выдача доступа | Запрет регистрации, MFA, совпадающий email в двух компаниях, приглашение, просрочка, перевыпуск, две конкурентные активации с одним успехом, сброс пароля, отзыв и ротация сессии | Тестовая почта доставляется в локальный каталог |
| Полномочия | Разделение платформенной и клиентской сессий, RLS под разными ролями, запрет мутации у viewer, блокировка сотрудника директором, запрет отключения последнего директора | Тесты покрывают репрезентативные мутации |
| Пересечение компаний | Изоляция на runtime/worker ролях, чужой ID файла, чужой ID инцидента и чужой клиентский аудит, раздельное выполнение импорта | Отдельно проверить браузерный переход A → B во время незавершённых запросов и будущую публичную выдачу tenant-выгрузок |
| Сбой источника | Ошибка структуры A, сохранение последнего успешного снимка, успешное обновление B, preview/approve/import, retry, аренда задания и дедупликация | Рабочие внешние интеграции и реальные сетевые сбои не участвовали |
| Поддержка и аудит | Оператор видит безопасные события и инциденты, причина из каталога, повторные ошибки дедуплицируются. Успех переводит инцидент на проверку, закрытие сохраняет аудит. Директор видит статусное изменение своей компании | Клиентский аудит ограничен покрытыми статусными изменениями. Полнота регистрации всех изменений и чувствительных чтений требует отдельной проверки |
| Приостановка и завершение | Проверены запрет публикации воркером после паузы, отзыв доступа при паузе и переход в closed через API. Отдельно в восстановленной копии выполнено удаление точного ID закрытой компании после проверки отсутствия активных источников и задач. Соседняя компания и её файл сохранились | Коммерческий процесс согласования выгрузки и сроков удаления требует отдельной приёмки |
| Совместимость | Отдельный сценарий заполняет схему на 005 и мигрирует до head, проверяет старые связи и политики. Реестр двух листов сохраняет неизвестную сумму и ручную стадию при повторе | Проверка исторических данных ограничена синтетическим набором |
| Восстановление | Обычный runner делает pg_dump, копирует вложения и выполняет pg_restore в другую БД одноразового кластера. Из восстановленных данных формирует ZIP с одним тендером и XLSX нужной компании. Проверяет хеш и отсутствие файла и UUID соседней компании | Покрыт выбранный срез тендеров и вложений. Полный tenant-граф, загрузка извлечённого набора в чистую систему, операторский экспорт и производственные RPO/RTO требуют отдельной репетиции |

## Результаты

- PostgreSQL 16, operations-only — прошли проверки дедупликации, RLS, безопасного контекста, аудита и восстановления инцидента.
- Интеграционный и legacy-сценарии — прошли проверку импорта, повторов, изоляции и сохранения снимка после сбоя.
- Полный API-прогон, включая composed auth, проверку пограничных состояний и scoped offboarding — пройден.
- Бэкап, восстановление и репетиция завершения заняли 2,06 с на локальном синтетическом наборе, из них извлечение ZIP — 0,05 с.
- Сборка фронтенда и браузерный smoke в Chrome прошли. Проверены входы директора и оператора с MFA и экраном кодов восстановления, открытие и обновление вложенных страниц, отказ чужому коду компании, карточка источника и инцидента, отзыв сессии и 404 неизвестных путей UI и API.
