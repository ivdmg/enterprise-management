# Центральный вход и границы ролей базы

Центральный вход включается через PLATFORM_AUTH_ENABLED. Обязательны разные HTTPS-хосты CLIENT_AUTH_ORIGIN и PLATFORM_AUTH_ORIGIN, отдельные учётные данные PostgreSQL DATABASE_RUNTIME_URL и DATABASE_PLATFORM_URL, случайный JWT_SECRET и Fernet-ключ AUTH_MFA_KEY. При включении INTEGRATIONS_ENABLED требуется третья роль DATABASE_WORKER_URL. В production дополнительно нужны AUTH_SMTP_HOST и AUTH_SMTP_FROM, SMTP-аутентификация задаётся через AUTH_SMTP_USER и AUTH_SMTP_PASSWORD при необходимости. Локальная проверка создаёт собственные роли и доставляет письма во временный каталог.

- Клиентская роль обращается к бизнес-данным в транзакционном контексте компании. Узкая функция auth_tenant_subject возвращает только ID компании и пользователя по точной паре code/email. Результат используется внутри аутентификации. Без активной сессии клиентский API закрыт.
- Платформенная роль получает сводки, операции доступа, ревизии, инциденты и ограниченные поля запуска. При подключении проверяется, что у роли отсутствуют прямые права на таблицы компаний, пользователей и предметных данных. Для управления интеграциями разрешены отдельные столбцы. Ссылки source_ref и secret_ref доступны для записи, чтение этих полей и отпечатка файла закрыто. Служебные проверки предпросмотра возвращают только признак действительности или срок подтверждения.
- Роль воркера читает ссылки на источники для конкретной компании, а полученные данные публикует в её контексте. Версии конфигурации и адаптера, состояние компании, поколение аренды и отпечаток файла проверяются перед публикацией.
- Миграционная роль владеет таблицами и функциями с повышенными полномочиями. Для runtime выдаются только нужные права. Проверяемая модель разрешений воспроизводится в auth_smoke.py и integration_smoke.py.

Первое приглашение владельца формирует команда python -m app.bootstrap_platform_owner --email <рабочий email> --name <имя> из backend в согласованной среде. Она использует платформенную роль, повторно отправляет приглашение только на тот же адрес до активации и не печатает токен. Приглашённый владелец задаёт пароль и включает MFA при первом входе. Одноразовые коды восстановления показываются один раз после настройки.

Приглашения компании попадают в зашифрованный outbox в одной транзакции с созданием записи. Черновик отправляется после активации компании. Перед отправкой проверяется актуальность приглашения. Ошибки доставки повторяются с задержкой. При исчерпании попыток панель показывает статус и владелец либо оператор по своим правам может перевыпустить ссылку. Отзыв, приостановка и закрытие гасят ранее отправленные токены.

При передаче полномочий владелец подтверждает старый и новый адрес директора. Преемник принимает приглашение и входит с MFA. После проверки владелец вызывает POST /api/v1/platform/companies/{company_id}/director-transfer с version, current_email, successor_email и reason. Операция требует Idempotency-Key, сохраняет историю и отключает сессии предыдущего директора. Прямое редактирование директора из клиентского списка команды заблокировано.

При ограниченной конфигурации обобщённые старые экраны и файловый каталог доступны только вместе с их предметными разделами. Это предотвращает чтение данных выключенного модуля через общий реестр. Настройка вида раздела включает название, порядок и доступность. Параметры источников проходят отдельную валидацию по каталогу адаптеров.
