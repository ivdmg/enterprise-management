# Панель поддержки и журналы

## Что видит специалист

Список компаний показывает статус обслуживания, подключённые модули и источники, время последнего успешного обновления, число открытых инцидентов и ответственного. Фильтры по состоянию, компании и тяжести. В карточке компании — разделы «Обзор», «Источники», «Инциденты», «Приглашения». Общеплатформенный сбой показывается отдельно от состояния конкретного клиента.

У источника состояния «ещё не проверен», «в работе», «актуален», «данные устарели», «требует вмешательства», «приостановлен». Свежесть считается от последнего успеха по сроку, установленному для источника. Сбой планировщика определяется по heartbeat. Зелёный HTTP health сам по себе не подтверждает свежесть данных. Указывать часовой пояс, доступна ли последняя успешная версия данных, и время очередной попытки.

Пример карточки: «Реестр поставок не обновился. В шаблоне пропала колонка “Дата поставки”. Последние подтверждённые данные от 09:30 доступны. Сверьте заголовки с владельцем источника. После исправления повторите проверку». Технические поля для передачи разработчику — код ошибки, время, идентификаторы запуска и запроса, версия адаптера и релиза, длительность, число обработанных строк. Без значений ячеек, ссылок с токеном и содержимого документов.

## Работа с инцидентом

| Событие | Действие поддержки |
| --- | --- |
| Таймаут или ограничение API | Проверить, идёт ли автоматический повтор. После исчерпания попыток эскалировать с идентификаторами запусков |
| Отозван доступ к источнику | Попросить владельца источника восстановить права. Проверить подключение и повторить импорт |
| Изменился формат | Сохранить последнюю успешную версию данных, запросить обезличенный пример, передать адаптер разработчику |
| Падение воркера или рост очереди | Сверить heartbeat и глубину очереди, эскалировать как общий инцидент при влиянии на несколько компаний |
| Подозрение на пересечение данных | Эскалировать владельцу платформы сразу. Ограничить затронутый доступ и импорты, сохранить следы, действовать по согласованной процедуре реагирования |

Инцидент проходит состояния «новый → в работе → передан разработчику → проверка → закрыт» с возможностью повторного открытия. Хранить ответственного, комментарий, время и ссылки на безопасные идентификаторы. Объединять повторные сбои по компании, источнику и коду, сохраняя историю попыток. Безопасный повтор добавляет задачу в очередь с проверкой прав, причины и активного запуска. Разработчик получает обезличенную карточку, без входа под сотрудником клиента.

## Три разных потока событий

- Операционный журнал поддержки. Код и понятное сообщение из каталога, время, степень влияния, компания и источник, следующий шаг. При отказе БД фиксировать только безопасный общеплатформенный сигнал в отдельном техническом канале.
- Клиентский аудит. Кто, когда и какое действие совершил, тип и ID объекта, результат, разрешённое описание изменившихся полей. Критичные успешные мутации и аудит записывать в одной транзакции. Директор фильтрует действия своей команды и видит, например, смену срока и автора. Аудит покрывает изменения, доступы, выгрузки и чувствительные чтения по согласованному перечню. Записи недоступны для редактирования клиентом.
- Технические логи. Доступ ограничен инженерным контуром, корреляция по request_id/job_id. Маскировать секреты, пароли, токены, тела запросов, строки файлов и данные из исключений на стороне источника события. Отдельно аудировать действия поддержки, включая открытие карточек и повторы.

Предлагаемые сроки для обсуждения — технические логи 14 дней, операционные события 90 дней, аудит 180 дней. Сроки и доступы утверждаются при подключении. Привилегированный разбор реального документа требует отдельного согласования и ограниченного по сроку доступа за пределами MVP.
