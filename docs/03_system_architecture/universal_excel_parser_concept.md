# Архитектура универсального парсера разнородных Excel-документов

Одной из главных технических сложностей при создании системы управления предприятием является обработка **неструктурированных и разнородных электронных таблиц (.xlsx, .xls, .csv)**.

---

## 1. Анатомия проблемы «Хаоса в Excel»

В реальных компаниях разные отделы и контрагенты создают таблицы по собственным правилам:
1. **Сложные и многоуровневые шапки**: объединенные ячейки (merged cells) в 2–4 строки, подзаголовки, метаинформация в первых строках (например, *«Утверждаю: Директор...»*).
2. **Нестандартные наименования колонок**:
   - *«Сумма договора»*, *«Цена контракта»*, *«Стоимость с НДС»*, *«Договорная цена»*, *«Объем руб.»* — все это означает одну бизнес-сущность: `contract_amount`.
   - *«Срок выполнения»*, *«Дата окончания СМР»*, *«Дедлайн»*, *«Период закрытия»* — означают `deadline_date`.
3. **Несколько несвязанных таблиц на одном листе**: например, сверху сводка по финансам, снизу реестр договоров.
4. **Итоговые строки и формулы**: строки *«Итого:»*, *«В том числе НДС»*, промежуточные итоги, которые нельзя путать с рядовыми записями.
5. **Грязные типы данных**: числа с пробелами (`1 250 000,00 руб.`), текстовые даты (`август 26`), спецсимволы, пустые ячейки.

---

## 2. Архитектура решения: 4-ступенчатый гибридный конвейер (Hybrid AI-ETL Pipeline)

Для достижения максимальной надежности, скорости и околонулевой стоимости мы используем **гибридный подход**, объединяющий быстрые алгоритмические эвристики и точечный семантический анализ через легкие LLM.

```
       [Загрузка Excel-файла (.xlsx / .xls)]
                         │
                         ▼
┌────────────────────────────────────────────────────────┐
│  ШАГ 1: Структурная нормализация (Fast Ingestion)       │
│  - Развертывание объединенных ячеек (Unmerge & Fill)   │
│  - Детекция областей данных (Table Bounding Boxes)     │
│  - Очистка пустых строк и декоративных шапок          │
└────────────────────────┬───────────────────────────────┘
                         │
                         ▼
┌────────────────────────────────────────────────────────┐
│  ШАГ 2: Эвристический профилировщик (Data Profiler)    │
│  - Анализ типов колонок (Даты, Деньги, %, Текст)       │
│  - Поиск и отделение строк итогов (Total / Summary)    │
│  - Сверка с локальным кэшем шаблонов компании          │
└────────────────────────┬───────────────────────────────┘
                         │ (Если шаблон новый)
                         ▼
┌────────────────────────────────────────────────────────┐
│  ШАГ 3: Семантический AI-маппинг (Semantic Column Map) │
│  - Отправка ТОЛЬКО заголовков и 2-х строк-примеров в   │
│    сверхдешевую LLM (Gemini Flash / DeepSeek V3)       │
│  - Маппинг на унифицированную онтологию сущностей      │
└────────────────────────┬───────────────────────────────┘
                         │
                         ▼
┌────────────────────────────────────────────────────────┐
│  ШАГ 4: Валидация, Сохранение и UI-Подтверждение       │
│  - Расчет Confidence Score (Уверенность распознавания) │
│  - Сохранение в унифицированную БД (SQLite / DuckDB)   │
│  - Возможность для пользователя скорректировать поле   │
└────────────────────────────────────────────────────────┘
```

## 3. Детальное описание этапов конвейера

### Шаг 1: Структурная нормализация (Raw Matrix Preprocessing)
- **Библиотеки**: `openpyxl` / `python-calamine` (сверхбыстрый парсер на Rust).
- **Развертывание объединенных ячеек**: если заголовок занимает диапазон `B1:D1` («Параметры договора»), а в `B2:D2` идут «Сумма», «Аванс», «Остаток», алгоритм создает составные заголовки: `Параметры договора_Сумма`, `Параметры договора_Аванс`.
- **Поиск реальной шапки таблицы**: алгоритм сканирует первые 15 строк, определяя строку с максимальным количеством текстовых ячеек и переходом к типизированным данным (числам/датам).

### Шаг 2: Алгоритмические эвристики и локальный кэш
- **Кэш шаблонов компании (Fingerprint Matching)**:
  Если компания каждый месяц загружает файл с одинаковой структурой колонок, система вычисляет хеш заголовков и **мгновенно применяет сохраненную схему** (0 секунд, 0 затрат на API).
- **Парсер денежных и временных форматов**:
  - Преобразование `1 500 000,50 ₽`, `1.5M`, `$ 400` в единый `float`.
  - Преобразование `18.09.2026`, `2026-09-18`, `18/09/26` в стандартный ISO `YYYY-MM-DD`.

### Шаг 3: Семантический LLM-маппинг (AI Schema Extraction)
Если структура не опознана локальным кэшем, формируется компактный JSON-запрос к легковесной модели (например, `gemini-1.5-flash` или `deepseek-chat`):

#### Пример входящего промпта в модель:
```json
{
  "task": "Map table columns to canonical business fields",
  "canonical_fields": [
    "project_name", "contract_sum", "paid_sum", "debt_sum",
    "deadline_date", "fine_amount", "status", "responsible_person"
  ],
  "detected_columns": ["Объект СМР", "Договорная цена, руб.", "Закрыто по КС", "Остаток к оплате", "Срок сдачи объекта", "Куратор"]
}
```

#### Ответ модели (Structured JSON Output):
```json
{
  "mapping": {
    "Объект СМР": "project_name",
    "Договорная цена, руб.": "contract_sum",
    "Закрыто по КС": "paid_sum",
    "Остаток к оплате": "debt_sum",
    "Срок сдачи объекта": "deadline_date",
    "Куратор": "responsible_person"
  },
  "document_category": "production_tenders",
  "confidence": 0.98
}
```
*Стоимость такого запроса: менее 0.0001$ (доли копейки), обработка занимает ~0.5 секунды.*

### Шаг 4: Унифицированная модель данных (Canonical Data Schema)

Все разнородные документы после парсинга приводятся к 4 стандартизированным бизнес-доменам:

```
┌────────────────────────────────────────────────────────┐
│               CANONICAL DATA SCHEMAS                   │
├────────────────────────────────────────────────────────┤
│ 1. Tenders & Production (Тендеры, СМР, Контракты)      │
│    - name, code, contract_amount, completed_amount,    │
│      remaining_amount, deadline, risk_level, fines     │
├────────────────────────────────────────────────────────┤
│ 2. Cashflow & Debt (Финансы, Касса, Взаиморасчеты)     │
│    - counterparty, incoming, outgoing, balance,        │
│      debt_direction, payment_due_date                  │
├────────────────────────────────────────────────────────┤
│ 3. Payroll & HR (ФОТ, Сотрудники, Выплаты)             │
│    - employee_name, department, accrued, paid, due     │
├────────────────────────────────────────────────────────┤
│ 4. Tasks & Compliance (Поручения, Налоги, Отчеты)      │
│    - task_title, due_date, status, penalty_risk        │
└────────────────────────────────────────────────────────┘
```

## 4. Пользовательский интерфейс проверки и подтверждения (Smart Preview)

Чтобы руководитель и менеджер на 100% доверяли данным, система предоставляет прозрачный UI:
1. Сразу после загрузки всплывает компактное окно сопоставления:
   - *«Мы распознали этот файл как „Тендерный план“. Вот как распределились колонки:»*
   - Зеленые бейджи с высоким уровнем уверенности (98%).
2. Если какое-то поле не распознано или пользователь хочет его переназначить, он делает это в 1 клик через выпадающий список (Select).
3. Система запоминает корректировку пользователя для всех будущих файлов этой компании.
