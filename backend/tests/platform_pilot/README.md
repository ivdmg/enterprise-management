# Изолированный стенд QA-01

Нужны Python 3.12 с зависимостями из `backend/requirements.lock.txt` и клиентские и серверные бинарники PostgreSQL 16. Запуск из корня репозитория.

```powershell
.\.venv\Scripts\python.exe backend/tests/platform_pilot/run.py --postgres-bin 'C:/Program Files/PostgreSQL/16/bin'
```

На Linux укажите каталог бинарников через `pg_config --bindir` и запускайте от обычного пользователя.

Команда создаёт одноразовый кластер PostgreSQL на случайном порту loopback, применяет миграции и запускает smoke-сценарий. Рабочие переменные окружения не наследуются. Для приложения копируются только код и миграции, поэтому его поиск `.env` и ключей ограничен временным каталогом. Сетевой сервер API и расписание импорта не стартуют. Кластер и локальные файлы удаляются после остановки.

- По три персональных клиента на компанию: директор, сотрудник с записью и сотрудник с чтением. Две компании получают разные книги с одинаковым именем и предметным номером 2501.
- Строительный реестр содержит два листа и неизвестную сумму контракта. Клиника получает синтетические данные поставки оборудования без данных пациентов.
- Подменяется только транспорт Drive для каждого запроса. Реальные FastAPI, парсеры, БД и файловый слой проверяют импорт, повтор без дублей, отсутствие чужих записей и запрет удаления файла другой компании. После повреждения реестра строительства API возвращает статус ошибки, ранее импортированные строки доступны, а клиника публикует обновлённый реестр.
- Тестовый почтовый адаптер сохраняет MIME-письмо в локальный outbox. Он проверяется пробной доставкой. Подключить его к приглашениям после появления интерфейса доставки.

Ограничения текущего smoke. Он проверяет существующий вход по email и ручной импорт через API. Раздельное планирование и автоматическая привязка источников, приглашения и вход оператора поддержки и владельца платформы относятся к сквозной приёмке после появления их контрактов. Укороченный реестр сейчас даёт техническую ошибку парсера. В QA-02 проверить понятное операционное событие для этого случая.

## Нагрузочный профиль QA-03

```powershell
.\.venv\Scripts\python.exe backend/tests/platform_pilot/run.py --postgres-bin 'C:/Program Files/PostgreSQL/16/bin' --load-only
```

Полный прогон занимает около 41 минуты. `--load-quick` сокращает окна для проверки самого сценария. Используются пять синтетических компаний, 50 учёток, по два локальных источника по 300 строк. API и воркеры получают разные непривилегированные подключения к PostgreSQL. Два воркера параллельно импортируют данные, а клиентские запросы идут с реальными cookie-сессиями и проверкой принадлежности строк.

Профили дают 6 запросов/с в течение 30 минут, 20 запросов/с в течение 10 минут и 200 запросов за 5 секунд. Отдельно проверяется одновременный вход 50 сотрудников с пяти тестовых адресов. JSON-строки результата содержат p95 от планового момента запроса, статусы HTTP, очередь, пересечение чтений с импортом, CPU-время и пиковую память процесса Python.

Запросы идут через ASGI без внешней сети и браузера. CPU и память включают API, фоновые задачи и генератор запросов, PostgreSQL измеряется отдельно только по очереди. Google Drive заменён локальными книгами. Эти результаты служат локальной проверкой приложения. Размер ВМ подтверждается отдельно на целевом окружении и реальном профиле импорта.
